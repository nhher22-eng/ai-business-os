# AI Business OS 한 장 비상 절차

## 1. 먼저 구분합니다

- **접근 문제**: 현재 Codex 작업공간·PC가 GitHub 또는 EC2에 연결되지 않음
- **개발 문제**: 코드 테스트 또는 빌드 실패
- **운영 문제**: 실제 사이트, API, PostgreSQL, Redis 또는 작업 실행 실패
- **데이터 위험**: 백업 누락, DB 손상 가능성, 삭제·덮어쓰기 위험

접근 문제를 운영 장애로 표현하지 않습니다. 항상 운영 영향과 데이터 안전 여부를 따로 확인합니다.

## 2. EC2에 접속합니다

Windows PowerShell:

```powershell
ssh -i "C:\Users\new\Downloads\ai-business-os-key (1).pem" ubuntu@3.35.202.64
```

키 파일이 없으면 새 키를 채팅으로 보내지 말고 AWS의 공식 복구 절차로 접근을 회복합니다.

## 3. 한 줄 진단을 실행합니다

```bash
aios-doctor
```

- `작업 진행 가능 여부: 가능` → 기준 브랜치와 커밋을 기록하고 진행
- `주의 후 가능` → 표시된 대체 경로를 확인하고 진행
- `중단` → 배포·DB 변경·삭제를 하지 말고 실패 항목부터 복구

## 4. 작업 시작 전 확인합니다

```bash
aios-preflight
```

반드시 확인할 항목:

1. GitHub 읽기
2. GitHub 쓰기 dry-run
3. 현재 브랜치와 커밋
4. 미커밋 변경
5. Docker 서비스
6. API·PostgreSQL·Redis
7. 최근 백업과 무결성
8. 디스크 사용률

## 5. 정상 경로가 막히면 대체 경로를 사용합니다

| 막힌 경로 | 대체 경로 |
| --- | --- |
| Codex → GitHub 쓰기 실패 | 사용자 PC → EC2 SSH → GitHub |
| 도메인 접속 실패 | EC2 공인 IP와 로컬 API 상태 확인 |
| 현재 채팅 작업공간 실패 | GitHub 최신 검증 브랜치에서 새 작업공간 시작 |
| GitHub 접근 실패 | EC2 로컬 Git 커밋과 검증된 Git 번들 보존 |
| 운영 DB 이상 | 최신 백업을 격리 DB에 먼저 복원·검증 |

## 6. 절대 바로 하지 않는 작업

- 운영 DB 삭제 또는 즉시 덮어쓰기
- 백업 확인 전 복구 명령 실행
- `git reset --hard`, 광범위한 파일 삭제
- 운영 브랜치 강제 푸시
- 비밀번호·토큰·PEM 키를 채팅이나 Git에 저장
- 원인을 모르는 상태에서 PostgreSQL·Redis 동시 재시작

## 7. 도움을 요청할 때 보내는 정보

다음 네 가지만 전달합니다.

1. `aios-doctor` 전체 결과
2. 문제가 시작된 시각
3. 마지막으로 실행한 명령 또는 화면 동작
4. 실제 사이트가 열리는지 여부

비밀번호, 토큰, `.env`, PEM 키 내용은 보내지 않습니다.
